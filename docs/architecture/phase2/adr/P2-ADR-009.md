## Context

`P2-ADR-002` correctly records the package decision made at P2-S00-02, but it
does not describe the final Phase 2 product. Subsequent authorized slices moved
LoopX from the 0.2.4 offline-wheel profile to a fixed, complete embedded-source
runtime. The final release evidence already verifies that newer boundary.

`P2-ADR-008` also compresses the final regression history too aggressively. Its
verification section says every full suite was rerun against one target. The
actual admitted evidence is stricter about provenance: exact full-regression
receipts were reused only across a validated linear commit chain, and the final
target received a bounded targeted supplement. Preflight, sealed validation,
release, cleanroom, and final freeze were run against the final target itself.

The original ADR files and their frozen digests remain unchanged so the
immutable `0485261...` policy-contract receipt stays reproducible. This ADR is
the later audit decision that resolves their current interpretation.

## Decision: final LoopX product boundary

The final Phase 2 product uses:

- version `0.2.13`;
- source ref `v0.2.13`;
- annotated source object `a2c072d412d90839132e1cf39c23dd431c394175`;
- peeled source-tree commit `7232dca45ec2ca996edc43b2d3558edc802c844e`;
- embedded tree digest
  `66af2de0082dbadf7c7cb3ffc85b9b91b889c0433103ea3bc05abb313d831961`;
- migration mode `pinned_embedded_source_integration`;
- vendor-like complete runtime boundary
  `packages/integrations/loopx_runtime/**`;
- Zyra-owned resolver, bridge, state, permission, error, event, API, UI, and
  behavior-test boundary
  `packages/integrations/zyra_integrations/loopx/**`.

The release runs this embedded source directly. It does not depend on an
archive-extraction path, `../long-horizon-systems/loopx`, an online repository,
a user-level installation, or a development cache. LoopX remains a
supplementary implementation and does not become a second canonical runtime or
state owner.

## Decision: exact verification provenance

The P2-S06-03 technical PASS is bound to target `0485261...` as follows:

1. The final preflight has 16 of 16 hard gates passing and retains 31 of 31
   required failure receipts.
2. Sealed validation contains two independently validated, zero-invalid-
   transition runs with 3,144 and 7,437 effective transitions.
3. Release admission has 14 of 14 mandatory receipts, cleanroom is ready, and
   the two release archives are byte-identical.
4. Final regression has 14 of 14 logical gates. It reuses the exact complete
   receipt at `7995b64...`, proves the 12-commit path to `0485261...` is linear
   and allowlisted at blob/mode/path level, and runs a 250-test plus 2-subtest
   target supplement together with policy-contract and internalization checks.
5. The final freeze audit evaluates 13 of 13 checks as true and returns `PASS`
   with no blocker.

This provenance satisfies the no-duplicate-heavy-execution rule. It does not
claim that the complete Python and Web suites were executed a second time at
`0485261...`.
