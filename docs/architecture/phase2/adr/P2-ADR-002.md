# P2-ADR-002: Pinned LoopX package, install profiles, and upgrade policy

- Status: Accepted and frozen

- P2 base commit: `e207b46ca690171139a718b8b85d808cb5a79c1e`
- Digest manifest: `config/phase2/contract-digests.json`
- Supersession: a new ADR is required for a version, source commit, package boundary, or state-owner change

## Decision

LoopX is a complete supplementary implementation package for long-horizon goal
control:

- version: `0.2.4`;
- source commit: `8e79843704a40d8069a9cab4ede6edc6d29f671b`;
- source language and target language: Python;
- migration mode: `pinned_package_integration`;
- production landing boundary:
  `packages/integrations/zyra_integrations/loopx/**`.

LoopX is installed as one coherent package. Its upstream runtime assets do not
count as Zyra-owned production implementation. Zyra-owned installation,
identity mapping, durable outbox, single-writer protection, permissions,
errors, events, API, UI, and behavior tests remain separately attributable.

## Install profiles

The two supported profiles must resolve to the same pinned source and digest.

1. `linux_wsl_upstream_semantics` preserves upstream installer behavior while
   explicitly assigning project-local bin, release, skill, manual, and runtime
   roots. It must not edit a user shell profile or install user-level
   competition state.
2. `windows_release_offline_wheel` installs a checksum-locked wheel/source
   artifact from the release bundle and runs an equivalent deep doctor. It
   does not execute POSIX-only `bash`, `chmod`, symlink, `tmux`, or `fcntl`
   assumptions as if they were Windows guarantees.

The competition release must install without network access and without
reading `../long-horizon-systems/loopx`, an online Git repository, a user home
state directory, or a development cache.

## State and concurrency boundary

LoopX state is workspace-local and isolated per run/goal. On Windows, only one
Zyra-owned adapter writer may update LoopX files. API and CLI callers enqueue
through that writer. Durable outbox records carry stable Zyra and LoopX
identities and idempotency keys. Restart replays unacknowledged records without
duplicating claims, spends, leases, or side effects.

Zyra commits its own canonical mutation before an outbox update. A LoopX sync
failure produces explicit `sync_degraded` state; it does not roll back an
already completed external side effect and does not silently claim success.

## Upgrade and rollback

An upgrade is a new pinned version and source commit, with a source archive
digest, license/SBOM update, upstream tests, Zyra integration tests, doctor,
state migration rehearsal, clean install, restart replay, and rollback proof.
Mutable tags such as `stable` cannot identify evidence. Uninstall or rollback
must preserve Zyra canonical state.
