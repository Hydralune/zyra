# M2 Worker Runtime And Tool Governance

M2 starts the heavy reuse phase. M0/M1 established the project spine; M2 must not continue with placeholder-only modules.

Current source landing:

- `vendor/claude-code-best` contains a project-local vendor copy of the `claude-code-best` repository, excluding `.git`.
- `vendor/browser-use` contains a project-local vendor copy of the `browser-use` repository, excluding `.git`.
- `packages/integrations/zyra_integrations/vendor_manifest.py` records the first migration groups and verifies they exist inside `zyra`.
- `apps/code-worker` defines the Node sidecar boundary for the vendored `claude-code-best` runtime.
- `packages/workers/zyra_workers/code_worker_bridge.py` provides the Python bridge to that sidecar.

Initial migration priority:

1. `CodeWorkerRuntime` sidecar from `vendor/claude-code-best`.
2. `BrowserWorker` adapter from `vendor/browser-use`.
3. `ToolPermissionRuntime` from `src/hooks/toolPermission`.
4. `SkillRuntime` from `src/tools/SkillTool`, `src/skills`, and `browser_use/skills`.
5. `SubagentRuntime` from `src/tools/AgentTool`.
6. Slash command integration from `src/commands.ts` and selected `src/commands/*`.
7. Compact and MCP adapters from `src/services/compact`, `src/services/mcp`, and `browser_use/mcp`.

Boundary rule:

- The runtime may temporarily be a TypeScript sidecar, but the sidecar source must stay under `zyra`.
- Python orchestration must communicate with the sidecar through structured events and adapter contracts, not direct imports from `../claude-code-best`.
- Later milestones should turn this vendor landing and sidecar boundary into deeper Zyra modules. M4 should connect compact/memory/skill-memory paths, M5 should connect recovery/scheduler/resource governance, and M6 should expose the runtime through a connected control console.
