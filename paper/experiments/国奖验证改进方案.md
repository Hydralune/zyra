# ZYRA 国奖验证体系改进方案

## 结论

导师指出的核心问题成立。第一版论文能够证明系统在两个指定长程场景中完成了无人干预闭环，但不能证明 ZYRA 相对单智能体、静态编排或主流多智能体框架具有普遍优势。国奖版本必须把验证工作从“展示系统能够运行”升级为“在冻结条件下比较不同方法，并由独立判分器量化任务质量、资源消耗和故障恢复”。

本轮已经完成两项补充。第一项是 150 个单元的真实模型在线先导实验，五种协作策略分别执行同一批任务；第二项是两个领域各 7 个变体、10 个种子的受控因果轨迹实验。在线先导实验可以进入正文，但必须明确其任务规模和适配器边界。因果轨迹实验只能放在附录，用于说明机制开关和证据链完整性。

## 已完成的在线先导实验

### 实验设计

任务要求系统从四组信息包中合成 12 项版本化要求。每个字段同时存在有效、过期和撤销记录，判分器要求选择版本号最高的有效记录。五种方法使用同一 DeepSeek V4 Flash 模型、相同输入记录、相同输出格式和相同判分器。方法执行顺序在每个任务、重复和故障条件区组内随机化。

五种策略如下。

1. 单智能体一次读取全部记录并生成答案。
2. 静态链式由四个 Agent 顺序更新同一份工作账本。
3. 静态星型由四个叶节点分别分析信息包，再由协调节点汇总。
4. 全量广播让四个 Agent 都读取完整记录，再由协调节点裁决。
5. ZYRA 根据待闭合义务定向路由记录，由专门节点产生局部交付；完成门检查全部字段，成员响应丢失时重派相关义务，判分失败时只修复未闭合字段。

实验覆盖 5 个不同任务、3 次重复以及无故障和成员响应丢失两种条件，共 150 个实验单元。运行产生 645 次真实模型调用，所有调用均返回 HTTP 200，并保存实际 Token、请求和响应字节、墙钟时间及输出摘要。实验没有读取历史轨迹。

### 主要结果

| 条件 | 单智能体 | 静态链式 | 静态星型 | 全量广播 | ZYRA |
| --- | ---: | ---: | ---: | ---: | ---: |
| 无故障 严格成功率 | 3/15 20% | 3/15 20% | 3/15 20% | 3/15 20% | 13/15 87% |
| 无故障 字段正确率 | 91% | 90% | 89% | 91% | 99% |
| 响应丢失 严格成功率 | 0/15 0% | 0/15 0% | 0/15 0% | 5/15 33% | 13/15 87% |
| 响应丢失 字段正确率 | 0% | 71% | 73% | 93% | 99% |

无故障时，ZYRA 的严格成功率为 86.7%，Wilson 95% 置信区间为 62% 至 96%；各基线为 20.0%，区间为 7% 至 45%。ZYRA 与每个基线的配对 McNemar 精确检验均为 p=0.001953，Holm 校正后 p=0.007813。ZYRA 相对四个基线的字段正确率平均提高 7.8 至 9.4 个百分点。

成员响应丢失时，ZYRA 成功 13/15，全量广播成功 5/15。二者配对比较中 ZYRA 独占成功 9 次，广播独占成功 1 次，McNemar 精确检验 p=0.021484。ZYRA 与单智能体、静态链式和静态星型比较均为 13 次独占成功、0 次反向独占成功，Holm 校正后 p=0.000977。

无故障时，ZYRA 平均使用 2,755 个总 Token，全量广播为 6,154 个，下降 55.2%；ZYRA 的平均智能体间通信量为 420 字节，全量广播为 16,124 字节，下降 97.4%。响应丢失时，ZYRA 为 3,280 个 Token 和 436 字节，全量广播为 6,061 个 Token 和 12,093 字节，分别下降 45.9% 和 96.4%。ZYRA 并不比单智能体节省 Token，无故障时也略高于静态链式；论文应将其优势表述为“以高于单智能体和链式的推理成本换取更高的严格完成率，同时显著低于全量广播的通信与 Token 开销”。

### 结果边界

这批数据仍不是国奖版验证的终点。

- 只有 5 个独立任务模板和 1 个模型。3 次重复反映运行波动，但不能替代更多任务种类。
- 任务是结构化信息整合，不代表软件工程、开放研究和终端操作的全部难度。
- 五种方法是统一接口下的原生策略适配器，不是 AutoGen、GPTSwarm、AgentPrune 或 G-Designer 的官方代码。
- 响应丢失发生在模型调用成功之后，用来隔离协作层的接管能力，不等同于真实 Provider 宕机。
- ZYRA 同时启用了义务路由、故障重派和完成门修复。当前结果支持组合策略，单个模块的因果贡献仍需消融。
- 以任务和重复编号作为配对单元会低估同一任务重复运行之间的相关性，因此显著性结果属于探索性证据。

## 因果轨迹实验的正确用法

本轮对软件交付和跨源研究两个封存档案分别运行 7 个变体和 10 个种子，共 140 个实验单元、4,480 条指标样本。变体包括单智能体、静态全连接、完整动态群体，以及关闭调度、记忆压缩、恢复和低冗余通信的四个消融。

代码审计发现，该执行器逐条读取同一份历史事件档案，再依据能力开关重建路由、通信、恢复和记忆结果。部分质量、Token、成本和路由时延来自显式公式，例如关闭调度后放大路由时延、启用记忆后按固定系数调整成本。这些指标不能作为真实端到端优势。论文应把该实验命名为“受控因果轨迹实验”，只报告以下内容：

- 不同策略产生的路由节点、边、消息接收者和拓扑变更是否符合定义。
- 关闭恢复后，已注入故障是否保持未闭合。
- 关闭记忆或压缩后，相应事件和回执是否消失。
- 证据包是否绑定代码版本、任务档案、种子和变体配置。

不得在正文使用该实验中的模型化质量分数、估算 Token、估算成本或 CPU 回放耗时来声称线上性能提升。当前执行器还把 `source_replay` 标记为 false，与实际逐条消费封存事件的行为不一致；对外材料必须采用本方案的证据边界说明，并在后续工程版本中修正字段命名。

## 国奖版主实验

### 研究问题与假设

主实验围绕四个可证伪问题组织。

1. 在相同模型、工具和预算下，ZYRA 是否提高最终可验证完成率。
2. 在完成率不降低的条件下，义务定向路由是否减少模型 Token 和智能体间通信。
3. 在需求变化、Worker 丢失、工具超时和网络分区下，ZYRA 是否提高恢复率并减少重复副作用。
4. 语义构图、环境修正、贡献剪枝、连续性门和租约恢复分别贡献了多少。

每个问题都要预先指定主要指标。任务完成以独立验证器通过为唯一主要终点；通信与成本只能在完成率同时报告的前提下解释；恢复成功必须满足新租约有效、工件重新验证、无旧代际提交和无未确认副作用。

### 基线与消融

正文至少保留五种内部策略：单智能体、静态链式、静态星型、全量广播和 ZYRA。外部对照选择两类即可，避免堆砌框架名称。

- AutoGen GroupChat 作为通用会话式多智能体基线，固定模型、工具和轮数上限。
- GPTSwarm 或 G-Designer 选择一个作为图式协作基线。若官方代码无法适配长程工具任务，应明确记录适配差异，不自行重写后仍沿用其名称。
- AgentPrune 适合用于通信剪枝对照，可放在结构化推理子集，不必强行覆盖故障恢复场景。

消融实验采用“一次只关闭一个组件”的配对设计：无动态拓扑、无环境修正、无贡献剪枝、无通信预算、无分层记忆与压缩、无连续性门、无租约恢复。消融不得通过固定惩罚系数修改最终分数，而应让变体独立执行任务，再由同一外部判分器评分。

### 任务规模

建议分三层执行。

| 层级 | 任务与规模 | 目的 |
| --- | --- | --- |
| 受控协作集 | 至少 20 个独立任务 每任务 5 次重复 | 统计比较拓扑、通信与版本冲突处理 |
| 领域长任务集 | 软件工程和跨源研究各至少 8 个任务 每任务 3 次重复 | 验证跨领域完成率、资源与连续性 |
| 真实试点 | 1 至 2 个合作场景 连续使用不少于 2 周 | 证明部署、用户价值和运维成本 |

软件工程任务优先从 SWE-bench Verified 或自建的冻结真实仓库问题中抽取，并使用隐藏测试判分。研究任务应冻结检索时间窗和来源集合，由独立事实表、引用完整性和盲评共同评分。任务难度需包含需求修订、跨文件修改、来源冲突和中途故障，避免全部是短问答。

### 通用指标

| 维度 | 主要指标 | 配套指标 |
| --- | --- | --- |
| 任务质量 | 独立验证通过率 | 字段或测试通过率 义务覆盖率 盲评质量 |
| 效率 | 总 Token 实际费用 墙钟时间 | 模型调用数 工具调用数 峰值上下文 |
| 通信 | 智能体间字节与 Token | 消息数 重复率 证据利用率 广播等价压缩比 |
| 稳健性 | 故障后最终通过率 | 恢复时延 重试次数 迟到提交 重复副作用 |
| 连续性 | 关键事实召回率 未决义务保持率 | 旧需求采纳 冲突事实接受 重复工件 |
| 合规 | 权限和隐私违规数 | 非法位置调度 未确认外部操作 |

“有效状态迁移数”可以保留为系统审计指标，但不能继续充当主要性能指标。正文首先展示任务完成、Token、时延、通信和恢复；有效迁移及事件类别放入附录。

### 统计方案

- 二元任务成功采用配对 McNemar 精确检验，并报告成功率的 Wilson 95% 区间。
- Token、时延和通信量采用配对随机化检验或 Wilcoxon 符号秩检验，同时报告配对差值的 bootstrap 95% 区间。
- 多基线和多消融使用 Holm 校正，不只展示未经校正的 p 值。
- 结果同时报告绝对差、相对差和效应量。p 值不能代替实际提升幅度。
- 以任务作为主要统计单元。若同一任务有多次重复，采用任务内聚合或分层模型，不能把字段、事件或消息当成独立任务扩大样本量。
- 在运行前冻结任务清单、主要终点、故障计划、排除条件和分析脚本。失败样本默认保留。

## 创新点的重新表达

论文应把创新收束为两个可验证命题。

第一，ZYRA 提出“义务图稳定、协作图动态”的双图控制方法。逻辑任务图保存必须完成的义务和版本，协作图只描述当前执行者与信息流。语义模型可以提议拓扑，但只有满足权限、隐私、资源、版本和图不变量的增量才能提交。与学习式拓扑工作的区别不在于都使用图，而在于 ZYRA 把动态图纳入持续任务状态和恢复协议。

第二，ZYRA 提出“证据消费驱动的连续性完成门”。系统不以 Agent 的完成声明终止任务，而是检查当前需求版本下的义务、工件、证据消费、关键事实和未确认副作用。该机制把通信剪枝、记忆压缩和故障恢复约束在同一个可验证终止条件下。在线先导实验已经显示完成门能够修复高字段正确率但未完全闭合的结果，下一步消融需要单独量化这一贡献。

相关工作应增加 AutoGen、GPTSwarm、AgentPrune、G-Designer、AFlow 和 MultiAgentBench 的逐项对比。比较维度包括拓扑是否在线变化、是否具有硬约束投影、是否维护版本化主状态、是否支持跨进程恢复、是否检查证据消费、是否面向端边云资源和是否提供独立完成门。

## 应用落地补强

应用价值不能只写“可用于软件、研究和运维”。建议选择一个容易取得证明材料的真实场景，例如实验室代码维护或课题组技术情报周报，连续试用两周并保存以下材料：任务清单、基线人工耗时、ZYRA 完成时间、一次通过率、人工接管次数、故障记录、用户评分、部署机器规格和模型费用。合作方出具的应用证明应说明实际使用日期、任务数量和可核验效果，不写泛泛的“具有良好前景”。

部署部分需要给出三档配置。

- 单机验证版包含 API、CLI、Web、数据库和一个模型 Provider，说明最低 CPU、内存、存储及安装时间。
- 局域网协作版增加独立 Worker 和边缘节点，说明网络、权限和证书要求。
- 生产试点版增加备份、监控、审计和回滚，给出每百次任务的模型费用与运维工时。

商业化部分可采用平台订阅、私有化部署和行业适配服务三种模式，但只有获得询价、试用或合作意向后再写收入预测。现阶段更可信的价值证明是减少重做、降低人工接管和提高可审计性。

## 当前可以写入论文的结论

当前证据支持谨慎结论：在包含版本冲突的受控在线信息整合任务中，ZYRA 的义务定向路由、响应丢失接管与完成门修复组合，相比四种原生策略基线取得更高的严格完成率；相比全量广播，模型 Token 和智能体间通信量明显更低。两个封存长程案例进一步证明系统能够在指定软件工程和跨源研究任务中完成无人干预闭环。

当前证据仍不支持以下表述：ZYRA 已普遍优于 AutoGen、GPTSwarm 或其他官方框架；ZYRA 在所有长程任务上具有统计优势；当前结果已经证明产业经济效益；受控因果轨迹中的估算成本和时延等同于真实线上开销。
