# 实验运行根因审计与重启门槛

日期：2026-09-09

## 1. 原始验证目标

实验要回答的不是“某一道 SWE-bench 题能否被反复跑通”，而是：在相同基础模型、任务输入、工具权限和资源上限下，ZYRA 相比官方单智能体和多智能体基线，能否在跨领域长程任务中提高严格任务成功率，并在故障和需求变化下改善恢复、通信与资源效率。主要终点必须来自官方评测器、隐藏测试或确定性状态检查。

## 2. 当前证据的有效性

- `pallets__flask-5014/run25` 是有效的端到端校准样本：ZYRA 任务终态完成，独立 SWE-bench 评测为 `resolved=1/1`，隐藏 FAIL_TO_PASS 与 60 个 PASS_TO_PASS 均通过。它只能证明链路可行，不能证明总体优势。
- Pylint 的 run1/run2 是环境或启动校准事故，不进入效果统计。
- Pylint run3 产出了生产代码和回归测试，人工以仓库归属入口复核为 `1 passed`，但代理自己的验证凭据失败，任务终态为 `needs_verification/failed`。按预注册规则它是失败单元，不能改写成成功。
- Pylint run4 在 33 次模型调用后仅留下 1 行生产修改，累计 974,546 Token，未添加回归测试，因总 Token 预算耗尽而失败。
- Pylint run5 是为根因审计主动取消的开发运行，不进入任何效果统计。
- 以上 Pylint 重复运行均属于系统开发和校准材料。由于已经据其结果调整过实现和提示，`pylint-dev__pylint-8898` 不再作为后续正文效果估计的独立正式样本。

## 3. 根本原因

### 3.1 实验阶段混淆

尚未通过 26 个能力匹配校准单元，就把开发运行标成 `formal` 并对同一任务重复调参，违反了“普通超时、Agent 错误计为失败，不按结果追加预算”的正式协议。继续刷同一道题只会产生选择偏差，不能增强论文证据。

### 3.2 累计预算与上下文压缩触发条件错位

run4 的首轮输入为 6,671 Token，末轮输入增长到 45,294 Token；33 轮累计输入 949,401、输出 25,145，总计 974,546 Token，其中缓存读取 890,496 Token。运行时压缩依据“当前上下文是否接近约 100k Token 窗口”触发，而总预算依据“每轮输入、包括缓存输入的累计值”扣减。因此上下文尚未达到压缩阈值，累计预算已经耗尽；run4 全程压缩次数为 0。

这不是提高总预算可以根治的问题。密封基准现改为 96,000 字符（约 24k Token）的工作上下文，使既有 compact/restore 机制在约 16k Token 附近介入；普通非基准任务仍保留原有大窗口。SWE-bench 启动脚本默认总预算恢复为统一的 600,000 Token 校准值。

### 3.3 完成门与验证凭据不一致

run3 的代理使用了会掩盖真实退出状态的管道命令，并直接执行功能测试夹具，而非仓库的功能测试入口。代码工作已经发生，但完成门没有合格的行为验证凭据，恢复器随后进入不适合代码任务的权限失败分支。运行时现明确要求使用归属测试入口并保留真实退出码；确定性收口仍要求同时存在生产修改、测试修改和成功的聚焦测试凭据，最终正确性仍由独立官方评测器决定。

### 3.4 配置测试没有覆盖有效行为

一次临时修改把读取阈值设为 1，但运行时会将该值夹到最小值 2；原单测只检查字典传播，因此出现“测试通过、行为未变化”。该调参已撤销。后续资源或策略参数必须同时测试：配置传播、运行时解释、端到端事件三层，不再以单层单测作为有效性证明。

## 4. 允许重新启动付费校准的门槛

在以下条件全部满足前，不再进行新的 API 重跑：

1. 密封基准的 96,000 字符上下文限制通过配置传播单测；
2. 使用模拟模型的多轮集成测试证明压缩事件会在预算耗尽前发生，压缩后仍能写入、测试和完成；
3. 失败验证只进入代码验证/修复路径，不再误路由到 BrowserWorker；
4. 运行记录能自动标记 `calibration`、`formal`、`invalidated-development`，开发运行不会混入统计；
5. 单次运行自动输出统一的状态、时间、Token、缓存 Token、工具调用、压缩次数、补丁摘要和官方评分字段；
6. 校准与正式任务使用预先冻结且对所有方法一致的任务族预算，普通失败不重跑。

通过上述门槛后，只允许一次新的、未据结果调优过的 SWE-bench 校准任务验证真实链路；该任务仍不进入正文效果统计。

## 5. 真正需要跑到的规模

### 阶段 B：先完成 26 个能力匹配校准单元

目标是证明四类系统的适配器、日志、预算和官方评分器一致，而不是比较优劣。任一系统的评分器或记录字段不一致就停止并修复。

### 阶段 C：公开宽度主实验

冻结的 54 个独立公开任务覆盖 SWE-bench Verified、tau2-bench、MultiAgentBench 和 AgentBench v0.2。ZYRA、AutoGen 静态团队和 Magentic-One 在能力匹配任务上成对运行；OpenHands 只覆盖其官方支持的任务。每题首轮一次，只有预注册的 18 个哨兵任务重复一次用于估计随机性。

### 阶段 D：压力与容错

24 个独立任务分别在正常和预注册扰动条件下运行三个系统，共 144 个主单元；关注任务内配对的成功率、恢复时延、约束违规和通信开销。

### 阶段 E：定向消融

六个核心模块各选 8 个相关任务，对比完整系统与单模块移除版本，共 96 个单元。只有这一阶段能够支持各模块“有贡献”的论断。

完整协议预计约 500–650 个有效单元。论文主结论必须来自独立任务的配对统计、95% 置信区间和多重比较校正；不能由 Flask 的一次成功或 Pylint 的重复尝试推出。

## 6. 下一步唯一正确动作

先完成第 4 节的无 API 门槛和自动证据汇总，再运行剩余校准矩阵。Pylint 当前失败保留用于暴露系统缺陷，不再继续刷题。若完成校准后 ZYRA 的成功率仍低，则应缩小论文主张或继续做系统研发，并重新冻结全新任务集；不能通过挑任务、改预算或重复到成功来“证明”成果。
