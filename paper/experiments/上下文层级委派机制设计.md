# ZYRA 上下文层级委派机制设计（第二步）

日期：2026-09-10

## 1. 动机

四道校准（django-15930 / pytest-6202 / matplotlib-13989 / sphinx-9367）暴露的共同模式：**单 agent 在密封基准下扛整个任务，上下文随 tool 历史线性膨胀，累计 provider token 因「每轮重放 + cache 计费」爆炸，最后 provider 准入 fail closed。**

第一步（commit `b0a8ef47`）修了两个根本机制：
- **A 账本脱节**：累计预算驱动压缩阈值收紧，预算过半强制压缩。
- **B 恢复丢状态**：跨 attempt 合并 obligation evidence，确定性收口。

但这两个修复本质仍是「单 agent 长上下文里打补丁」——它们压缩的是**历史**，没有改变「一个 agent 的上下文里塞进全部探索轨迹」这个结构。本设计从结构上消除这个病根：**把任务拆成子任务，每个子任务在 isolated 上下文里独立执行，父 agent 只持有「目标 + 子任务摘要 + 交付状态」的紧凑上下文。**

## 2. 现状（代码事实）

1. **benchmark 工具清单**：`packages/workers/zyra_workers/code_worker_runtime.py:137` 用 `default_tool_registry()`（`packages/runtime/zyra_runtime/tools.py:259`），只含 `file_read`/`file_write`/`file_edit`/`shell`/`shell_wait` 等基础工具，**不含 Agent/Task 委派工具**。
2. **TS 侧委派机制已存在**：`packages/runtime/claude-runtime/src/agents/agent-tool.ts` 的 `TypeScriptAgentRuntime` 暴露 `Agent`/`Task`/`agent_status`/`agent_cancel`/`agent_wait`/`agent_result`/`agent_resume`/`agent_message`/`agent_list` 九个工具，支持 `context_mode: isolated|fork|resume`、`isolation: workspace|worktree|sandbox|remote`、后台 fanout。
3. **E03 委派执行器**：`spawn()` 通过 `E03AgentControlCoordinator` + `HostE03PhysicalPort` + `runChild` 物理 spawn 子 agent，子 agent 走独立 `RuntimeRunInput`，有独立 budget（`DEFAULT_AGENT_BUDGET`：12 turns / 48 tool calls / 64k input tokens）。
4. **断层**：benchmark 的 `provider-control-plane` 路径，模型拿到的 `tools` 来自 Python `registry.list()`（`typescript_claude_runtime.py:1534`），**Agent 工具从未进入这个清单**，所以模型在密封基准下「看不到」委派工具，只能自己扛。

## 3. 目标架构

```
┌─────────────────────────────────────────────────────────┐
│  父 agent（orchestrator，紧凑上下文）                     │
│  - 目标 + 交付契约                                        │
│  - 子任务拆解规划                                         │
│  - 每个子任务的「一句话摘要 + 已提交 workspace delta」      │
│  - 不持有任何子任务的 tool 历史 / 源码细节                 │
└──────────────┬──────────────────────────────────────────┘
               │ Agent(tool) 委派，context_mode=isolated
     ┌─────────┴─────────┐
     ▼                   ▼
┌──────────────┐   ┌──────────────┐
│ 子 agent A    │   │ 子 agent B    │
│ "定位缺陷"    │   │ "写回归测试"  │
│ isolated 上下文│   │ isolated 上下文│
│ 只回报摘要+delta│   │ 只回报摘要+delta│
└──────────────┘   └──────────────┘
```

**核心不变式**：父上下文只随「子任务数量」线性增长，不随「每个子任务的 tool 调用历史」增长。子 agent 的探索轨迹在它自己的 isolated 上下文里，结束后只把「结果摘要 + 已提交 workspace delta + verification receipt」回流给父。

## 4. 关键设计决策

### 4.1 委派触发：不是「模型自主决定」，是「预算压力驱动」

不让模型自由决定何时委派（那会引入「乱 fan out」风险）。而是在**父 agent 的累计预算过半时**（复用第一步 A 的 `budgetForcesCompaction` 信号），父 agent 收到一条系统级 steer 指令，引导它把「当前未完成的子任务」委派给 isolated 子 agent，而不是继续在自己膨胀的上下文里探索。

这与第一步 A 形成互补：
- 第一步 A：预算过半 → 压缩历史成摘要（治标）。
- 第二步：预算过半 → 把「新工作」委派出去（治本），父不再碰新探索。

### 4.2 子任务拆解：SWE-bench 的最小拆解

对「定位 + 修复 + 验证」这类任务，父 agent 至少可以拆成：
1. **定位子任务**：读源码、复现、定位根因 → 回报「根因 + 目标文件 + 修复方案」。
2. **修复子任务**：实施最小生产改动 → 回报「改动文件 + diff 摘要」。
3. **验证子任务**：跑聚焦回归测试 → 回报「pytest 退出码 + receipt」。

每个子任务 isolated，父只拿摘要。这样父的上下文里永远是「3 条摘要 + 3 个 delta」，而不是「40 次 tool 调用的完整轨迹」。

### 4.3 上下文隔离：isolated，不是 fork

`context_mode=isolated`（而非 `fork`/`resume`）是核心——子 agent 拿到**干净上下文**（只有子任务 prompt + 必要文件路径），不继承父的膨胀历史。这是「降级」的含义：子 agent 在降级的局部上下文里解决子问题，父 agent 保持在全局视角。

### 4.4 结果回流：只回摘要 + 已提交 delta

子 agent 的 `finalText` 只取「一句话结论 + 结构化交付证据」（workspace delta、verification receipt），不回 tool 历史。复用第一步 B 已建立的 `obligation_evidence` 结构。

## 5. 实现路径（分阶段）

### 阶段 1：暴露委派工具（最小改动）
- `default_tool_registry()` 或 benchmark 特定 registry 加入 `Agent`/`Task` 工具 spec（schema 从 TS `agent-tool.ts:45` 的 invocationSchema 同步过来）。
- 让模型在 benchmark 下「看得到」委派工具。

### 阶段 2：接通委派执行器
- benchmark 的 `provider-control-plane` 路径下，`Agent` 工具调用路由到 TS `TypeScriptAgentRuntime.execute()`。
- 确保 `runChild` + `host` 在 benchmark 物理环境能 spawn 子 agent（复用 E03 coordinator）。

### 阶段 3：预算压力驱动的委派 steer
- 父 agent 累计预算过半时，注入系统 steer 指令「把当前子任务委派给 isolated 子 agent」。
- 与第一步 A 的 `budgetForcesCompaction` 对齐。

### 阶段 4：回归测试 + 端到端验证
- 确定性回归：覆盖「父预算过半 → 委派 → 子 isolated 执行 → 摘要回流 → 父上下文不膨胀」。
- 新题端到端跑。

## 6. 风险与权衡

| 风险 | 说明 | 缓解 |
|---|---|---|
| **委派额外 token 开销** | 每个子 agent 有独立 prompt + 输出，短任务上委派可能比单 agent 更贵 | 只在预算过半（长任务）触发；短任务单 agent 直接做 |
| **子任务上下文丢失** | isolated 子 agent 看不到父已发现的关键线索 | 委派 prompt 里显式携带「父已确认的根因/文件路径」 |
| **物理 spawn 在 sealed 环境的隔离** | benchmark 容器隔离下，子 agent 的 workspace 访问需正确授权 | 复用 E03 的 isolation 语义（workspace/容器） |
| **SWE-bench 单 bug 任务收益有限** | 定位+改+验证强耦合，拆开可能丢上下文 | 本机制主要服务「超长程多子任务」场景，SWE-bench 是验证载体 |

## 7. 与第一步的关系

- 第一步 A（累计预算驱动压缩）+ 第二步（预算压力驱动委派）是**同一信号的两条路径**：预算过半时，既压缩历史，又引导把新工作委派出去。
- 第一步 B（恢复续跑）保证委派出的子 agent 结果能跨 attempt 确定性收口。
